# The Copy — контекст розробки AI NPC

## 1. Проєкт та розподіл відповідальності

- **The Copy** — кооперативна 3D-головоломка на Unity для двох гравців із науково-фантастичним сюжетом у дослідницькому комплексі.
- Дипломна тема: **«Модель адаптивної поведінки NPC для комп’ютерної гри у жанрі кооперативної головоломки»**.
- NPC «Копія» може допомагати гравцям у головоломках, спостерігати за ними або перешкоджати відповідно до контексту сцени.
- **Моя зона:** NPC AI, perception, short-term memory, ML decision maker, вибір цілей, керування діями NPC, навігація й інтеграційний код NPC.
- **Напарник:** мережа, фізичні механізми, ігрові головоломки, основні сцени та сценарні тригери. Інтеграцію й тестування виконуємо спільно.
- Voice Chat уже частково реалізовано напарником; для NPC потрібно інтегрувати інформацію про голосову активність / рівень звуку, а не переписувати VoIP.

## 2. Обов'язкові функціональні вимоги

- **NPC-01:** багатоджерельне сприйняття — звук/голос, світло, простір, ігрові події.
- **NPC-02:** контекстна поведінка — Assist / Observe / Obstruct із правилами сцени.
- **NPC-03:** динамічний вибір пріоритетної цілі та стійкість проти безпідставних перемикань.
- **NPC-04:** короткострокова пам'ять недавніх подразників, позицій та їхнє згасання.
- **NPC-05:** переривання, захист критичних дій, коректне відновлення / скасування.
- **NPC-06:** фізичні взаємодії NPC із головоломками, важелями та механізмами.
- **NPC-07:** природний рух, NavMesh, анімація й зрозумілий зворотний зв'язок.

**Обов'язкова умова:** саме **Decision Maker має бути ML/нейромережею**; суто Utility AI не відповідає вимозі дипломної роботи. Інші модулі можуть бути C# / Unity.

## 3. Узгоджена концептуальна архітектура

`World/VoIP/Scene Events → Perception → Short-Term Memory + Scene Context → ML Decision Maker → Intent(action,target) → Action Controller → Navigation/Interaction/Animation`

- ML вибирає **високорівневу дію та ціль**, а не керує безпосередньо фізикою чи рухом.
- C# забезпечує сенсорний препроцесинг, пам'ять, маскування недопустимих дій, сценарні обмеження та виконання.
- Початковий метод — **Unity ML-Agents + PPO + компактна MLP**, тренування офлайн, inference із `.onnx` у Unity.
- Рекомендована мережева схема — **host-authoritative NPC**: рішення та стан авторитетно обробляються хостом, клієнти отримують синхронізацію. Це попередня рекомендація, яку потрібно звірити з реальним мережевим кодом команди.
- Потрібно відокремити навчальний симулятор від production-інтерфейсів та перевіряти їхню відповідність.

## 4. Напрацювання та їхній поточний статус

### Етап 0 — вимоги

- Сім вимог NPC-01…07 та матриця їхнього покриття.
- П'ять базових сценаріїв: реакція на звук/пам'ять, конкурентні подразники, контекстна поведінка, переривання критичної взаємодії, кооперативна головоломка.
- Основні інтеграційні договори ще потрібно підтвердити за реальним репозиторієм.

### Етап 1 — середовище

У попередньому окремому тестовому Unity-проєкті працювали:

- Unity Editor **6000.6.5f1**;
- Unity ML-Agents Unity package **4.1.0**;
- Conda Python **3.10.12** в env `project-s-ml`;
- Python `mlagents==1.1.0`;
- PyTorch **2.2.1+cu121** із `torch.cuda.is_available() == True` на RTX 4060;
- офіційний приклад 3D Ball: навчання та inference `.onnx` пройдені.

Це конфігурація **тестового проєкту**; версію Unity/пакети командного репозиторію НЕ припускати автоматично такими самими.

### Етап 2 — ML proof of concept

- Спрощена симуляція: 3 спостереження (sound/light/security) та 3 рішення (Continue/Investigate/Observe).
- Порівняно модель із випадковою політикою на 500 контрольних випадках.
- Mean reward: ML **0.51628**, random **0.1963**.
- Частка оптимальних рішень: ML **79.8%**, random **33.4%**.
- Проблема: на тихому сценарії QuietNormal ML обирала Continue лише **21%** проти **26%** у random. Це слід дослідити під час перероблення reward / динаміки; не вважати модель готовою для гри.

### Етап 3 — Perception & Memory

- Експериментальна реалізація звукових, світлових і сценарних подій, затухання сигналів, short-term memory та фіксованого вектора з **17 чисел**.
- Автоматичний звіт: **10/10 PASS**, `observationCount=17`, Unity 6000.6.5f1.
- Це тести спрощеної сцени, **не** підтвердження інтеграції з реальним Voice Chat/Flashlight/NGO.

### Етап 4 — ML Decision Maker (не завершено)

- Експериментальна модель: **27 спостережень** (17 із Stage 3 + 10 ознак цілей/дій), 7 дискретних рішень:
  0 Continue;
  1 Investigate sound;
  2 Investigate light;
  3 Observe Player A;
  4 Observe Player B;
  5 Assist mechanism;
  6 Obstruct mechanism.
- Застосовувалося маскування недоступних дій.
- PPO: два прихованих шари по 128; план 150 000 кроків на запуск; порівняння seed 11/22/33; ID/OOD сценарії.
- Спостерігалися `UnityTimeOutException`, одне навчання перервано біля 3016 кроків, пізніше запуск досяг приблизно **60 000 кроків**. Етап 4 НЕ закритий; фінальної валідації 3 seed / ID / OOD немає.
- Не стверджувати, що експериментальна `.onnx` — готова production-модель.

## 5. Нове рішення щодо організації розробки

Переходимо від окремого навчального Unity-проєкту до **існуючого командного Git-репозиторію в окремій feature-гілці**. Не створювати інший Unity-проєкт для фінальної NPC-системи. Окремі тестові/навчальні сцени всередині спільного проєкту допустимі.

- Не переносити всі Stage 2/3/4 C#-скрипти без аналізу: вони були написані для ізольованого прототипу.
- Спочатку вивчити реальні системи: мережа (зокрема NGO), Player, Voice Chat, світло, сцени, механізми, інтеракції, структури подій.
- Перевірити робочу гілку Git, чистоту робочого дерева та командні домовленості. Не створювати гілку/commit/merge без явного завдання.
- Запропонувати інтеграційні межі і план поступового перенесення прототипів, що не зачіпає чужих систем без необхідності.
- Для ML: підтримувати відтворювані YAML-конфігурації, seeds, результати оцінювання та версії моделей, але не комітити гігантські training artifacts / Library.

6. Окремо задокументувати невизначеності, ризики та інтерфейси, що потрібно погодити з напарником.

## 7. Правила взаємодії

- Пояснення й документи — **українською**; назви C#-сутностей, API й код за потреби англійською.
- Перевага чітким покроковим завданням, а не широкому переписуванню архітектури.
- Перш ніж редагувати, називати файли, наслідки змін і спосіб перевірки.
- Не вигадувати реалізації, файли чи результати тестів. Розрізняти «перевірено», «припущення» та «потрібно узгодити».
- Не змінювати чужі мережеві й ігрові механіки без явної необхідності та погодження.
- Не допускати чистого Utility AI як фінальної заміни ML Decision Maker.
