## Вхідні дані та маніфест

Один JSONL-запис має поля старого `the-copy.intent-evaluation/1`, але нову **schema=`the-copy.attention-evaluation/1`**. Додаткові обов’язкові поля:

- `observations`: ті самі 50 чисел, за якими NN отримала маску й робила вибір;
- `profile_id`: `the-copy.expert-attention/1`;
- `dataset_id`: ідентифікатор версії набору;
- `decision_outcome`: явне розділення вибору та технічного результату, описане нижче.

Це новий формат offline-входу, не зміна observation contract. Поточний C# recorder не записує 50-вектор і не створює цей формат. Старі traces не можна доповнити вигаданими або повторно захопленими спостереженнями: потрібен майбутній runner P4-05.

Перед збором випадків зберігається JSON-маніфест:

```json
{
  "schema": "the-copy.attention-case-manifest/1",
  "dataset_id": "example-only-v1",
  "split": "diagnostic",
  "cases": [{"case_id": "example-1", "scenario": "competition"}]
}
```

Маніфест непорожній, case_id унікальні. Потрібен один термінальний запис на випадок; дублі, сторонні case_id, інший scenario/dataset/split відхиляються. Відсутні записи відображаються в `missing_case_ids`, `complete=false`. Маніфест потрібен навіть для порожнього JSONL: інакше неможливо розрізнити «не було випадків» і «всі відповіді загублено». Сам файл не доводить, що його створили до вимірів; це обов’язок протоколу запуску й версіонування P4-05.

Один звіт — один run/policy/seed/split. Seeds не змішуються в пул випадків. Майбутній аналіз незалежних запусків повинен показувати результати кожного seed окремо та їхню варіативність. Розмір наборів, seeds і train/ID/OOD розподіл ще не зафіксовані цим зрізом.

## Вибір, доставка й технічні відмови

- `decision` + `accepted`, без reason: отриманий вибір. Reward обчислюється на початковому знімку. Помилково прийнята недоступна дія або некоректний payload додатково збільшує `accepted_invalid_count`.
- `decision` + `rejected` із `masked_or_unavailable` / `malformed`: оцінюється початковий вибір, але прийнятим результатом він не є. Наприклад, спочатку дозволена дія могла стати недоступною до callback; початковий reward не підтверджує успішну доставку.
- `stale` + `rejected`, reason=`stale`: reward відсутній.
- `technical_rejection` + `rejected`: authority_denied / configuration_invalid / perception_unavailable / target_changed. Reward вибору не обчислюється. Це виключення не є нульовою винагородою й не змінює математичну шкалу.
- `no_response` або `cancelled` + `no_response`: action/target/latency=null, reward відсутній. Причину збережено в самому записі; наявний technical evaluator може звітувати її детальніше.

Суперечливі outcome/status/reason відхиляються. Невідомі причини потребують явного доповнення формату, не автоматичного трактування як успіх. Початкові невалідні вектори — помилки даних, усього звіту успішно не створюється. Відмови ще до захоплення валідного вектора поки відображаються як відсутній запланований випадок; їхню причину повинен зберігати окремий журнал майбутнього runner-а.

## Метрики й знаменники

`R` — погоджений reward. Нормалізований regret=`1-R`; за недоступного вибору R=−1, regret=2. Near-optimal — **допустимий початковий вибір** із regret≤epsilon. `epsilon` задається явно в [0,1), без default; числова похибка порівняння 1e-12 зазначена у звіті. Рівні максимуми всі оптимальні; baseline argmax обирає найменший індекс лише для відтворюваності.

- `selection_mean_reward`, `selection_mean_regret`, `near_optimal_selection_rate`: тільки `decision`, включно з відхиленими виборами. Поруч завжди показані scored count і coverage.
- `accepted_near_optimal_rate_of_planned`: прийняті near-optimal вибори з коректною формою payload / **усі випадки маніфесту**. Missing і technical зменшують цю частку, але не отримують вигаданий reward.
- `accepted_invalid_count`: прийняті порушення початкової маски або форми payload. Це діагностика, не доказ безпечності фізичних взаємодій.
- Paired baseline/gain: тільки ті самі знімки, на яких є оцінюваний NN-вибір. Random — точне очікування uniform-allowed із Continue; mask-rule — перший доступний сенсорний намір; argmax — 1 за побудовою. Додатково baseline показані на всіх наявних знімках, включно з technical, щоб було видно покриття. Порівняння умовне й може мати selection bias при відмовах; coverage не можна приховувати.
- `overall` — micro, однакова вага кожного випадку. `by_scenario` — окремі результати. `macro_by_scenario` — однакова вага кожного запланованого scenario. Якщо хоча б один scenario не має оцінюваних виборів, відповідне умовне macro=`null`, а coverage показується явно. Для частки прийнятих рішень від запланованих повністю відсутній scenario дає 0.

Reward оцінює **індекс наміру**, не координати. Accepted-частка довіряє статусу producer-а й перевіряє лише форму target. Вона не доводить правильність ID/позиції: це окремі reference/target-метрики й Unity-інтеграційні тести. `record_provenance` прямо каже, що походження переданих векторів незалежно не доведено.

## Погоджені критерії проміжного експерименту

Для цього обмеженого проміжного експерименту користувач погодив:

1. epsilon=**0.05** — допустима втрата до 5% від максимальної експертної оцінки одного знімка.
2. Основна метрика — macro `accepted_near_optimal_rate_of_planned`: **ID≥0.90**, **OOD≥0.80**. Це погоджені інженерні цілі, не емпірично обґрунтовані властивості гри й не перенесені пороги Stage4.
3. Обов’язково повний маніфест (`complete=true`) та `accepted_invalid_count=0`; показувати coverage й відмови. Нуль порушень у наборі не є гарантією для всіх майбутніх станів.
4. Random, mask-rule й argmax порівнювати на тих самих випадках. Не вимагати довільного позитивного gain у кожному scenario: у quiet всі правильні baseline отримують 1. Показувати конкуренцію сигналів окремо; не заявляти перевагу NN над argmax цієї ж шкали.
5. Модель обирати за ID; OOD відкривати лише для підсумкової оцінки. Набори й критерії зафіксувати до вимірів, кількість випадків/запусків узгодити під час P4-05.

Evaluator перевіряє JSON на відповідність реалізованій версії критеріїв. За split=id/ood та epsilon=0.05 `quality_checks` містить повноту маніфесту, нуль прийнятих некоректних payload/масок та поріг основної macro-метрики. Усі три умови мають виконатися. `quality_gate` — `pass_on_supplied_records` або `fail_on_supplied_records`. Це результат на переданих записах, не незалежне підтвердження їхнього походження чи готовності gameplay-моделі. Train/diagnostic повертають `not_assessed_train_or_diagnostic_split`, інший epsilon — `not_assessed_nonprotocol_tolerance`; у цих випадках checks=null. Підбирати epsilon за OOD заборонено протоколом.

CLI повертає 0 за коректно сформований звіт, навіть якщо він має fail або неповний маніфест. Код процесу **не** quality PASS; споживач повинен перевіряти `quality_gate` і `quality_checks`. Некоректні записи відхиляються з кодом 2 без нового успішного звіту. Збережений старий report у тому самому output-path автоматично не видаляється: майбутній runner має використовувати унікальні run-path і перевіряти код процесу.
