## 1. Мета та принцип роботи з планом

Створити у **спільному Unity-проєкті Project S** NPC «Копія» з адаптивною поведінкою для двох гравців у кооперативній головоломці. NPC сприймає події, пам'ятає нещодавні подразники, обирає **поведінку і ціль за допомогою навченої ML-моделі**, виконує дії через звичайні системи Unity, працює з механізмами гри та узгоджено відображається в мережевій сесії.

**Обов'язкова вимога керівника:** модуль **Decision Maker є справжньою ML/нейромережевою моделлю**. Суто Utility AI / Behavior Tree / `if-else` як остаточний Decision Maker не відповідає дипломній темі. Класична логіка дозволена для сенсорів, пам'яті, правил сцен, фільтрації недопустимих дій, навігації та виконання. Utility AI можна реалізувати як **порівняльну базову модель**.

**Джерело правди щодо поточного коду — реальний командний Git-репозиторій, а не цей документ.** До редагування Codex повинен перевірити файли, API, гілку, залежності та наявні реалізації. Жодне припущення про готовність мережі, VoIP чи механізмів не вважати доведеним без аналізу коду.

### 1.1. Порядок роботи

1. Працювати у спільному Git-репозиторії, **у погодженій feature-гілці**, а не в новому ізольованому Unity-проєкті.
2. Навчальні та тестові **сцени всередині спільного проєкту** допустимі; існуючі сцени напарника не змінювати без потреби та погодження.
3. Починати кожен етап із перевірки залежностей і критеріїв прийняття; завершувати доказами (тести, логи, CSV, сцени, демонстрація).
4. Перед зміною існуючих файлів пояснити, **які саме файли** змінюватимуться, для чого і як перевіряти результати.
5. Оновлювати цей план після значущих рішень і фактично завершених робіт; не підміняти результати симулятора фактами про production-гру.

## 3. Архітектурна концепція та межі відповідальності

```text
VoIP / Player / Lighting / Puzzle / Scene Events
                        |
                        v
                 Perception (C#)
                        |
              +---------+----------+
              v                    v
       Short-Term Memory       Scene Context (C#)
              +---------+----------+
                        |
                        v
        Observation Builder + Target Candidates
                        |
                        v
         ML Decision Maker (PPO / MLP, ONNX)
                        |
               Intent(action, target)
                        |
                        v
     Action Controller + scene constraints (C#)
                        |
            Navigation / Animation / Interaction
                        |
              Host authority + Network sync
```

**Зона власника NPC:** Perception, Memory, формування спостережень, ML Decision Maker, логіка вибору цілей, Action Controller, навігаційний/анімаційний код NPC, адаптери до наявних систем та тестування його підсистем.

**Зона напарника:** базовий Voice Chat / VoIP (уже частково існує), мережевий транспорт, стани та правила фізичних механізмів, основні головоломки, сцени, сюжетні тригери. Підключення й інтеграційні випробування — спільні.

**Мережа:** попередній вибір — **host-authoritative NPC**: одна авторитетна інстанція виконує ML-рішення і взаємодії, клієнти отримують синхронізовані стани/анімації. Перед реалізацією звірити з наявною системою мережі та погодити з напарником.

**Фінальне навчання:** офлайн. У runtime Unity запускається inference навченої моделі; постійне онлайн-перенавчання не є вимогою MVP.

## 4. Перевірений технологічний фундамент і фактичний прогрес

### 4.1. Перевірено в **окремому тестовому** Unity-проєкті (не в командній грі)

- Unity **6000.6.5f1**; `com.unity.ml-agents` **4.1.0**.
- Conda env `project-s-ml`, Python **3.10.12**, Python `mlagents==1.1.0`, PyTorch **2.2.1+cu121**, CUDA доступна на RTX 4060.
- Офіційний 3D Ball: навчання, експорт `.onnx` і inference перевірені.
- **Stage 2:** 500 тестів; mean reward ML **0.51628**, random **0.1963**; частка оптимальних дій **79.8%** проти **33.4%**. `QuietNormal` — слабке місце (**21%** оптимальних дій ML). Це лише proof of concept.
- **Stage 3:** автоматичний `stage3_test_report.json`: **10/10 PASS**, вектор **17 ознак**; VoIP/ліхтарик гри ще не інтегровані.
- **Stage 4:** прототип **27 ознак** (17 Stage 3 + 10 ознак кандидатів), 7 дискретних варіантів «дія+ціль». Навчання розпочато, було перервано; один запуск досяг орієнтовно **60 000 з 150 000** кроків. **Не підтверджено** завершення 3 запусків, ID/OOD-оцінювання, фінальний поріг або придатність `.onnx` для гри.

- [ ] **P6-02** Підключити облік двох гравців і стабільну ідентифікацію цілей (не покладатися на довільний порядок об'єктів).
- [ ] **P6-03** Імплементувати погоджену host/server authority для NPC і клієнтське відображення його стану.
- [ ] **P6-04** Синхронізувати фізичні взаємодії NPC з механізмами та станами головоломок.
- [ ] **P6-05** Відтворити SC-01…SC-05 на наявних сценах гри або погоджених інтеграційних тест-сценах.
- [ ] **P6-06** Перевірити перепідключення/втрату гравця, спірну взаємодію, мережеву затримку в межах реальних можливостей проєкту.

**Результат:** NPC в ігровій сцені, спільний двокористувацький тест і журнали синхронізації.

**Критерій завершення:** в обох гравців узгоджені дії, позиція й результати взаємодій NPC; немає незалежних суперечливих ML-рішень на клієнтах. **Статус:** не розпочато.

### Етап 7 — Системне тестування та експериментальне оцінювання

**Орієнтир:** 2–4 тижні. **Мета:** кількісно підтвердити корисність ML Decision Maker та надійність NPC у реальній грі.

**Задачі**

- [ ] **P7-01** Узгодити фінальні тест-кейси, критерії успіху й кількість повторень **до** тестування.
- [ ] **P7-02** Реалізувати простий **класичний baseline** (наприклад Utility AI) **лише для порівняння**, не замінюючи ML.
- [ ] **P7-03** Порівняти ML, random і класичний baseline за однаковими стартовими ситуаціями (за можливості парні seeds).
- [ ] **P7-04** Виміряти: успішність задач, релевантність рішень, затримку рішення, частоту перемикань цілей, недопустимі дії, FPS/CPU/GPU.
- [ ] **P7-05** Перевірити незнайомі/модифіковані сценарії та стійкість до пропущених/шумних сигналів.
- [ ] **P7-06** Провести аналіз помилок, зафіксувати обмеження й відтворюваність методики.

**Результат:** контрольні набори, CSV, графіки, порівняльні таблиці, пояснення невдач і фінальний висновок за метриками.

**Критерій завершення:** є відтворювані дані, що дозволяють оцінити переваги/слабкості ML порівняно з baseline, без вигаданих результатів. **Статус:** не розпочато.

### Етап 8 — Стабілізація, документація та захист

**Орієнтир:** 1–2 тижні. **Мета:** стабільна демонстрація і матеріали для дипломної роботи.

**Задачі**

- [ ] **P8-01** Зафіксувати й перевірити фінальну модель, observation/action contracts, версії залежностей і конфіги.
- [ ] **P8-02** Переконатися, що проєкт збирається з чистого клону за інструкцією; відсутні випадкові локальні залежності.
- [ ] **P8-03** Підготувати демонстраційну сцену і сценарій показу адаптивної поведінки для двох гравців.
- [ ] **P8-04** Оформити результати експериментів, графіки, переваги, обмеження, практичні висновки.
- [ ] **P8-05** Оновити технічну документацію, README, changelog, схему компонентів, правила відтворення навчання.
- [ ] **P8-06** Підготувати демонстрацію/запис для захисту й перевірити всі ключові сценарії.

**Результат:** стабільний AI NPC у грі, фінальна модель, відтворювані експерименти, демонстрація та матеріали дипломної.

**Критерій завершення:** інша людина може зібрати/запустити проєкт за документацією; демонстрація підтверджує NPC-01…NPC-07 і роль ML Decision Maker. **Статус:** не розпочато.

## 7. Орієнтовна тривалість, залежності та пріоритети

| Етап | Орієнтир   | Основні залежності                                  |
| ---- | ---------- | --------------------------------------------------- |
| 0    | 1 тиждень  | Потреби гри, погодження вимог                       |
| 1    | 1–2 тижні  | Версії командного Unity, середовище, контракти      |
| 2    | 2–3 тижні  | Unity ML-Agents, мінімальна симуляція               |
| 3    | 2–3 тижні  | Інтерфейси ігрових подій, початкова сцена           |
| 4    | 3–5 тижнів | Схема спостережень/цілей, Stage 3, тестові сценарії |
| 5    | 2–4 тижні  | Action/Interaction API, доступність механізмів      |

| 7    | 2–4 тижні  | Працездатна інтегрована версія, контрольні набори   |

Початковий генеральний орієнтир: **близько 4–6 місяців** за частково паралельної роботи; це **не** жорсткий дедлайн і не оцінка часу, який залишився після вже проведених експериментів. Тривалість повторно оцінити **після аудиту командної гри**.

**Критичний шлях:** `Audit/Migration → Contracts → Perception/Memory → ML Decision Maker → Action Controller → Co-op Integration → Experiments → Demo`. Частину тестів, документації й адаптерів можна розробляти паралельно.

## 8. Робочі правила для Codex (обов'язкові)

1. **Почни з read-only аудиту**, вказуй шляхи до реальних файлів/класів. Не переписуй чинну гру «з нуля».
2. Не стверджуй, що етап виконано, якщо є лише код без Unity-перевірки, чи якщо POC пройшов тести, але інтеграція не перевірена.
3. Перед змінами формулюй: **мета → файли → очікувана поведінка → тести → ризики**.
4. Не створюй/не перемикай Git-гілку, не коміть, не роби merge/push, не змінюй чужі механіки без явного запиту й погодження.
5. При зміні кількості/порядку спостережень або набору дискретних дій: онови версію контракту, PPO-конфіг і заново перевір сумісність `.onnx` (за потреби перенавчи модель).
6. Коли додаються нові інтерактивні об'єкти з відомою семантикою, віддавай перевагу спільному інтерфейсу кандидатів, але не обіцяй узагальнення без тестів.
7. Для оцінювання фіксуй: код/commit, Unity/пакети, PPO YAML, seed, модель, набори сценаріїв, метрики, дату, логи. **OOD-набір не використовувати для підбору моделі.**
8. Після завершення робіт оновлюй таблицю статусу та задачі, записуй конкретні докази. Невідоме позначай як `Потребує перевірки`.
9. Пояснення й документацію пиши українською; C#-назви й API залишай відповідно до кодової бази.

## 9. Definition of Done та журнал рішень

### 9.1. Правило закриття задачі

Задача вважається `Done`, лише якщо:

- є конкретний результат (файл/клас/модель/документ);
- відтворено тест або демонстрацію, що відповідає критерію;
- збережено шлях до доказу (логу, CSV, скриншоту, тест-звіту або commit);
- відомі обмеження та вплив на наявний Unity-код;
- зміни сумісні з поточною командною гілкою або явно задокументовано блокер інтеграції.

### 9.2. Рекомендовані статуси

`Backlog` → `To Do` → `In Progress` → `Blocked` / `Review` → `Done`.

Для ранніх напрацювань, які були перевірені **тільки в окремому Unity-проєкті**, використовувати позначку **`POC verified; game integration pending`**, а не `Done` для спільної гри.

### 9.3. Формат запису задачі

```text
ID: P4-03
Назва: Затвердити production-схему observation/action
Власник: NPC developer
Статус: To Do
Залежності: MIG-03, P3-07, погоджений API цілей
Зміни: (реальні шляхи після аудиту)
Перевірка: автоматичний тест довжини/порядку/діапазонів + inference smoke-test
Докази: (шляхи, commit, звіти — заповнити після виконання)
```

### 9.5. Відкриті питання після аудиту репозиторію

- Яка фактична версія Unity та пакети командної гри? Чи сумісна поточна ML-Agents-конфігурація?
- Яка саме бібліотека Voice Chat і де доступні per-player рівень гучності / voice activity?
- Як у грі отримати Player ID/позицію, стани світла, сценарні тригери й доступні механізми?
- Яка мережева схема авторитетності (host/server), де запускати inference, як відображати стан NPC на клієнтах?
- Які наявні сцени й об'єкти придатні для першого реального інтеграційного тесту?
- Яку версію observation/action contracts зафіксувати перед **production-навчанням**, а які критерії прийняття встановити?

**Наступна дія P4-03:** погодити серверний NPC-API першого вузла живлення та джерело спостережуваних гравців. Перевірена чернетка входів готова. Після узгодження кандидатного блоку затвердити фінальну схему й шлях перевірки моделі. Пакети й тривале навчання потребують окремого погодження.
