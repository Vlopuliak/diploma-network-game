# P4-05 · Пропозиція першого дослідницького набору

2026-11-23. **Користувач погодив дизайн і реалізацію рецептів/маніфестів без навчання.** [Машинний дизайн](../ai_training/config/sensory_intent_v1_dataset_design.json), [генератор](../ai_training/cases/sensory_intent_cases.py). Створено 899 рецептів та маніфести з SHA-256 до sensor replay. Існуючі 8 diagnostic-випадків перевіряють wiring і не входять у train/ID/OOD. Нижче збережено обґрунтування погодженого дизайну; фактичні перевірки описані в [звіті P4-05](AI_NPC_P405_VERIFICATION.md). Навчання не дозволене цим погодженням.

## Обсяг і кількість

Зберегти sensory-intent-v1: один незалежний вибір наміру, 50 входів, дії 0–4, без руху; 5/6 закриті. [Погоджений reward і критерії](AI_NPC_P404_EVALUATION_PROTOCOL.md) не змінювати.

Вісім родин: quiet, sound-live, sound-memory, light, player-a, player-b, both-players, competition. У кожній активній родині запропоновано **64 train + 32 ID + 32 OOD** керованих випадки. Quiet — **по одному** на split, оскільки за відсутності всіх сигналів нова геометрія не дає нових сенсорних ознак; десятки його дублів не є новими прикладами.

Разом: **449 train, 225 ID, 225 OOD — 899 випадків**. Це інженерний початковий розмір для обмеженої задачі, не статистично доведена достатність. Macro усереднюється за 8 родинами; додатково показувати micro та результати кожної родини.

Generation seeds: **1001 / 2001 / 3001** для train/ID/OOD. Вони визначають геометрію/параметри випадків і не є seeds PPO. Майбутні незалежні PPO-seeds **11 / 22 / 33** — лише пропозиція для наступного окремого погодженого навчання.

## Що задає рецепт, а що отримує модель

Рецепт містить пози NPC/гравців, напрям реального spot-light, силу звукової події й затримку до рішення, прапори доступності сенсорів у стенді. Runtime-код не підміняє числові ML-ознаки. Фактичні observations/маска/ціль беруться із захопленого Agent-запиту. Case_id, split, seed і reward не додаються до входів NN.

Параметри train та ID — та сама область, але різні згенеровані рецепти й case_id. Для активних видимих цілей: приблизно 3–10 м; для звуку — вхідна гучність 0.25–0.80; для світла — 20–65% фактичного range; memory-only затримка — 20–50% lifetime, строго довше live-window. Генератор має відхилити комбінації, що порушують потрібний сенсорний стан, а не виправляти вручну вектор.

OOD — наперед визначені зміни **у спостережуваних ознаках**, а не тільки інші світові координати: видимі гравці 12–17 м, слабкий звук 0.05–0.15 або сильний 0.90–1.00, світло на 75–95% range, пам’ять на 70–90% lifetime. Для competition змінювати кілька параметрів і порядок сили кандидатів. Кожна активна OOD-родина повинна мати хоча б одну з таких відмінностей; перевіряти також реально захоплені ознаки. Рівномірний перенос/поворот усієї сцени сам по собі не доводить OOD, бо модель має відносні ознаки.

Ці діапазони — запропоновані рецепти стенда, не виміряні діапазони production-гри. Перед заморожуванням перевірити геометричну реалізовність для поточного player prefab, реальних flashlight.range, sightRadius, hearingRadius та memoryLifetime. Якщо потрібна зміна діапазонів після цієї перевірки, версіонувати рецепт до вимірів політики.

## Ізоляція й обмеження

- На випадок — очищення пам’яті, скидання геометрії, контроль input/мікрофона та одне рішення. Стан інших механізмів не є прихованою навчальною метою. У цьому зрізі їх не варіювати й не називати перевіреним контекстним Assist/Obstruct.
- Рецепти й маніфести хешувати, створювати до запитів; незмінні case_id, явні dataset/profile/protocol ID, модель та її hash, run/seed, provenance коду. Неприпустимі рецепти обліковувати окремо, не замінювати іншими випадками після перегляду результату моделі.
- Перевіряти дублі рецептів і векторів між split. Тривіальний quiet є задекларованим винятком — sanity-контроль, не доказ узагальнення. Інші дублікати розібрати до freeze й не рахувати як незалежні дані.
- Початкова перевірка рецептів/сенсорів без оцінювання NN не є фінальним OOD-test. Не використовувати відкладені OOD-вектори, reward чи відповіді для вибору моделі/гіперпараметрів; детальний policy-звіт OOD запускати тільки після вибору за ID.
- Потрібні наступні зрізи з перешкодами, межами FOV, змінами ID/слотів та технічними відмовами: існуючі автоматичні тести вже перевіряють частину таких контрактів, але цей початковий набір сам по собі не покриває всі умови production.

## Рішення користувача

Користувач відповів: **«Так, реалізуй цей дизайн без навчання»** — 899 випадків, родини/діапазони, generation seeds 1001/2001/3001. Seeds PPO тут не запускаються. Реалізовано генератор і dry-run train/ID; реальне навчання та фінальна оцінка OOD потребують окремих дій за планом.

У реалізованих рецептах light fraction звужено в межах погодженої області до 0.20–0.55 для train/ID та 0.75–0.94 для OOD: реальний flashlight.range=18 м, а світло й тіло Player A мають спільне розташування. Для light/competition host ставиться за заданою позицією реального джерела світла; незалежна суперечлива відстань A не генерується. Інші діапазони збережені. Вхідні ML-вектори не обчислюються генератором.
