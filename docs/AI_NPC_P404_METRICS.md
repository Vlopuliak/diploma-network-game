# P4-04 · Метрики однокрокового вибору наміру

**Подальші результати:** [server-only JSONL-producer підключено й перевірено](AI_NPC_P404_TRACE_VERIFICATION.md), включно з реальним CPU-inference та окремими контрольованими callback-ами. Після погодження користувача окремо реалізовано [offline-reward експертної уваги](AI_NPC_P404_REWARD.md); загалом 61/61 Python PASS. `intent_metrics.py` лишається evaluator-ом без reward, старі trace-файли не оцінюються новою формулою. Нижче описано історичний початковий крок метрик до producer-а й погодження reward.

## Обсяг, погоджений 2026-11-19

Користувач обрав: **«Поки підготувати метрики й тести; reward не фіксувати до окремого обговорення»**. Тому цей результат є частиною P4-04, а не завершенням задачі reward. Немає формули винагороди, ваг, автоматичного oracle, заданого пріоритету звук/світло/гравці або нових порогів якості політики. Навчання не запускається.

Результат — [intent_metrics.py](../ai_training/evaluation/intent_metrics.py), який перевіряє й агрегує передані записи sensory-intent-v1, та [25 нових тестів](../tools/tests/test_intent_metrics.py). Інструмент не вибирає дії, не змінює Agent, не впливає на гру й не є Decision Maker. Критерії поточного кроку: відтворювані обчислення, коректні знаменники, явне трактування відсутніх даних, розрізнення спроб і прийнятих рішень, відсутність прихованого reward.

## Формат записів

JSONL, один запис на один запит рішення. Schema: `the-copy.intent-evaluation/1`; input_schema: `the-copy.decision-input/sensory-intent-v1`.

Цей формат передбачає, що валідний вхід і його маску вже захоплено для запиту. Помилки початкової підготовки/захоплення потрібно окремо обліковувати в майбутньому producer-і; не вигадувати для них успішно захоплену маску й не приховувати їх під час оцінювання повної системи. No_response тут означає відсутню відповідь на такий запит, а не будь-яку помилку запуску Unity.

Обов’язкові поля:

- `case_id`, `scenario` — непорожні назви випадку й групи. case_id у межах одного звіту має бути унікальний; повтори потребують окремих ID.
- `run_id`, `policy_id`, `split`, `seed` — контекст запуску. split = train/id/ood/diagnostic. Один звіт не може змішувати різні політики, запуски, розбиття чи seeds.
- `allowed_actions` — сім bool **на момент захоплення знімка**, 0=True, 5/6=False. Це доступність намірів, не еталон правильної відповіді.
- `action` — обраний індекс або null. Цілі числа поза діапазоном не викидаються зі статистики, а рахуються як порушення. Bool замість індексу заборонений.
- `target` — null або об’єкт із `source_client_id` (uint64/null) та `position` (три скінченні світові координати). ID 0 є гравцем Host; null — анонімне джерело. Для Continue цілі немає, для сенсорних намірів вона потрібна; звук може мати анонімне джерело, світло й видимі гравці — визначений ID.
- `status` — accepted/rejected/no_response. Для rejected потрібен явний `rejection_reason`, наприклад masked/stale/authority_denied/malformed. Це стан передавання наміру з Agent, **не виконання фізичної дії**.
- `latency_ms` — виміряний час відповіді або null. Для майбутнього producer-а вимірювати монотонним реальним часом від запиту до отримання відповіді, перед її відхиленням/прийняттям. Це затримка всього рішення з плануванням, не чистий час model worker. Поточний інструмент читає переданий вимір, сам його не вимірює.

Для no_response поля action/target/latency_ms мають бути null: timeout не можна видавати за виміряну затримку відповіді. Час очікування до timeout, якщо потрібен, слід зберігати окремо, а не підмішувати в ці latency-метрики.

`reference_outcomes` — необов’язковий список явно заданих допустимих еталонних відповідей `{action, target}` або null. **Еталони наразі не визначені для дослідницького набору.** Інструмент не виводить їх із масок, сили сигналу чи власного правила. У тестах вони штучні й слугують лише перевірці арифметики. Порожній список заборонений: відсутність еталона позначається null. Кілька еталонів дозволяють явно описати неоднозначність без прихованого пріоритету. Кожний еталон має бути допустимим у початковій масці.

Поточний Agent має серверну подію прийнятого рішення й лічильники, але не формує повний JSONL цього формату з причинами всіх відмов, timeout і вимірами latency. Producer реальних записів ще потрібно додати й перевірити разом із навчальними/контрольними випадками. Цей крок його не реалізує й не видає старі текстові Unity PASS-логи за дослідницькі дані.

## Метрики без еталонів

- Кількість випадків, відповідей, accepted/rejected/no_response та частки accepted і no_response від усіх випадків.
- `mask_violation_attempt_count` — відповіді з обраним індексом, якого немає в початковій масці; rate ділиться на число відповідей. Відсутня відповідь не є спробою обрати дію.
- `delivered_invalid_decision_count` — accepted-рішення, що суперечить масці або має семантично некоректну пару action/target. Відхилена спроба 5/6 не є прийнятим порушенням. Водночас accepted=5/6 не замовчується.
- Причини відмов окремими лічильниками.
- Число наявних вимірів latency, їх середнє, медіана та p95 методом найближчого рангу: елемент із номером ceil(0,95 × n) у відсортованій вибірці, починаючи з 1. Невідомий час не підмінюється нулем. Без вимірів ці величини null.

Звіт має загальний блок `overall` та окремі `by_scenario`. Автоматичного об’єднання train/ID/OOD, різних моделей або seeds немає. Оцінки латентності на кількох синтетичних записах не описують продуктивність Unity або NN.

## Метрики лише за явно заданих еталонів

`reference_count` і `reference_coverage` завжди показують, для скількох випадків є еталони. Якщо їх немає, accuracy-поля дорівнюють **null**, а не 0 чи 1.

- `intent_accuracy` — частка випадків із еталоном, де обраний індекс збігається з одним еталоном, без перевірки цілі.
- `selection_accuracy` — частка випадків із еталоном, де індекс доступний, action/target коректні й збігаються з одним еталоном. Враховує вибір **до** фільтра доставки: правильний вибір може пізніше стати простроченим.
- `accepted_reference_success_rate` — частка випадків із еталоном, де selection_correct і status=accepted. No_response та відхилена відповідь не є успіхом доставки.
- `target_accuracy` — частка правильних цілей серед випадків із еталоном та правильно обраним **цільовим** типом наміру. Missing target у цьому знаменнику є помилкою. Continue не має цілі й до цього знаменника не входить. Потрібно дивитися разом із intent_accuracy і загальним selection_accuracy.

Ціль збігається за ID та евклідовою відстанню до еталонної позиції. `--target-tolerance` задається **явно**, без прихованого значення за замовчуванням. 0,05 м у тесті — параметр синтетичного fixture, не погоджений поріг експерименту. Це точність адресації спостережуваної позиції, не успішність прибуття NPC.

Звіт зберігає `reward_status=not_defined`, `policy_quality_conclusion=not_assessed` та повідомлення, що походження переданих записів незалежно не перевірялося. Не має mean_reward, оцінки успіху головоломки чи висновку, що NN краща за baseline.

## Перевірки та відтворення

```powershell
python -B -m unittest discover -s tools/tests -v
python -B ai_training/evaluation/intent_metrics.py --records tools/tests/fixtures/synthetic_intent_records.jsonl --target-tolerance 0.05 --output Logs/AI-NPC/P4-04-metrics-synthetic-20261119.json
```

Інструмент і тести використовують лише стандартну бібліотеку Python, нові залежності не встановлювалися. **25/25 нових + 15/15 попередніх = 40/40 PASS** на системному Python 3.13.7 і в ML-середовищі Python 3.10.12. [Системний журнал](../Logs/AI-NPC/P4-04-metrics-tests-20261119.log), [ML Python](../Logs/AI-NPC/P4-04-metrics-tests-py310-20261119.log). CLI також перевірено з некоректним записом: код 2, файл успішного звіту не створюється.

[Синтетичний fixture](../tools/tests/fixtures/synthetic_intent_records.jsonl) містить три записи: прийнятий Continue, відхилену заборонену спробу та відсутню відповідь. CLI-вихід перевірено окремими assertions: 3 випадки, 1 спроба порушення, 0 прийнятих порушень, 2 виміри latency. [Діагностичний JSON](../Logs/AI-NPC/P4-04-metrics-synthetic-20261119.json). Ці числа штучні; не є результатом запуску політики.

Тести охоплюють порожні дані, відсутні еталони/latency, різницю ID 0/null, анонімний звук, неправильний ID, відсутню ціль, межу tolerance, кілька еталонів, masked attempt проти accepted invalid, stale, no_response, NaN/Infinity, bool замість індексу, дублі випадків, змішування splits/seeds/policies та незмінність вхідних записів.

Ігровий C#, Agent, контракти 50 ознак, пакети й сцени цього разу не змінювалися. Unity-компіляцію/інтеграційні тести не повторювали: нова зміна є ізольованим Python evaluator-ом, його перевірено без запуску гри. Попередні Unity-результати залишаються доказами своїх зрізів.

## Статус і наступний крок

**P4-04 · In Progress.** Метрики та їхні перевірки готові. Reward, еталони дослідницьких випадків, рівень прийнятної якості та критерії порівняння політик **не зафіксовані за рішенням користувача**. Доступність дії не визначає її корисності, тому формулу винагороди не можна автоматично взяти з масок.

Перед P4-05/навчанням потрібно окремо обговорити навчальну мету, джерело еталона/наслідку та baseline. Потім — зафіксувати формулу reward і критерії до оцінювання, визначити producer записів та контрольні випадки. Історичні ID/OOD-пороги Stage4 не перенесено. Фізичні результати NPC залишаються поза однокроковим сценарієм і перевірятимуться після Action Controller.
