## Формули

Для кожного дозволеного наміру обчислюється `u`:

- `InvestigateSound`: індекс 13 за наявності memory (12), інакше індекс 1 live. Навіть сильніший live не замінює доступну memory: це відповідає вибору цілі чинним C#-адаптером. Freshness вдруге не множиться.
- `InvestigateLight`: індекс 25. При `approximateAim=1` дія недоступна.
- `ObservePlayerA/B`: `0.01 + 0.99 * (1 - distance)`, distance — індекс 44/49. Навіть на межі нормалізації видимий гравець має позитивний бал.
- `Continue`: 1 у відсутності доступних дій 1–4, інакше 0.
- Недоступні дії мають `None` у списку оцінок і виключаються з максимуму.

За допустимого вибору `reward = u(action) / max(u allowed)`. Некоректний індекс або недоступна дія — −1. Некоректний знімок/маска — `ValueError`, без reward. `delivered_reward` повертає `None` для явних `no_response`, `stale`, `cancelled`; `decision` означає отриманий дискретний вибір, зокрема спробу вибрати замасковану дію. Невідомий outcome відхиляється.

Валідація перевіряє 50 скінченних чисел у діапазонах кодера, бінарні прапори, нульові відсутні блоки, позитивні силу/freshness, категорію звуку, known/value і маску кандидатів. Вона не доводить походження даних із гри, реальну геометрію чи відсутність застарівання. Це обов’язки збору випадків і серверної перевірки.

Рівні ваги різних сигналів і floor 0.01 — погоджені експертні припущення. Цільові координати не є NN-виходами; правильність адресації оцінюється окремо від цієї винагороди.

## Baseline та використання API

`baselines(..., rng=random.Random(seed))` повертає:

- `uniform_allowed_action`: рівномірний random серед усіх дозволених, включно з Continue. Додатково `uniform_expected_reward` — точне математичне очікування на одному знімку.
- `first_allowed_sensory_action`: перша дозволена дія в порядку 1,2,3,4, інакше 0; окремо її reward.
- `argmax_expert_action`: максимум цієї ж шкали, при рівності — найменший індекс; reward завжди 1. Це оптимальний baseline за побудовою. NN не може перевершити його за цією ж формулою.

Приклад із кореня репозиторію для вже захоплених `observations` та `allowed_actions`:

```python
import random
from ai_training.evaluation.expert_attention import load_profile, reward, baselines

profile = load_profile()  # Відхиляє непідтримувану версію або змінені формули JSON.
score = reward(observations, allowed_actions, action)
comparison = baselines(observations, allowed_actions, rng=random.Random(11))
```

Формули v1 фіксовані в коді; JSON — перевірюваний опис, а не довільний конфігуратор ваг. Зміна формул потребує нової версії профілю та тестів. API не змінює передані масиви й не використовує глобальний RNG.

Чинний `intent_metrics.py` лишається окремим evaluator-ом технічних JSONL без reward. У recorder-і немає повного 50-вектора, тому не можна заднім числом оцінювати старі trace-файли цим профілем. Майбутній runner має передавати вектор і маску того самого запиту, зберігати `profile_id` та явно відділяти доставку від вибору. Автоматичне перетворення `status/rejection_reason` у reward поки не реалізоване.
