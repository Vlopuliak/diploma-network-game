## Обсяг і критерії

Результат — серверний CopyDecisionInputV2 отримує сенсорний знімок v1 та поточну видимість двох гравців, зберігає їхнє зіставлення зі слотами A/B і кодує їх у новій версії числових входів. Перевірки: стабільність слотів, видимість і маски, відсутність прихованих координат та числових ID, нормалізація, очищення невдалого читання, disconnect, despawn і збереження попередніх контрактів.

Файли: [CopyDecisionContractV2](../Assets/Scripts/AI/TheCopy/CopyDecisionContractV2.cs), [CopyDecisionInputV2](../Assets/Scripts/AI/TheCopy/CopyDecisionInputV2.cs), [перевірки](../Assets/Tests/AI/P403DecisionV2Verification.cs). ## Знімок та ідентичність

`CopyDecisionSnapshotV2`, схема `the-copy.decision-snapshot/draft-2`, містить CopyPerceptionSnapshot v1 та необов’язкові PlayerA/PlayerB типу CopyPlayerObservation. Час береться з Perception.CapturedAt. Усі видимі гравці повинні мати ту саму часову мітку. У поточному читачі захоплення відбувається синхронно в одному ігровому кадрі.

CopyPlayerSlots використовує Client ID лише як метадані реєстру NGO. Під час першого читання A/B отримують два найменші підключені ID; порядок ConnectedClients або порядок виявлення не впливає на результат. У звичайному Host/Client це A = Host ID 0, B = Client ID 1. Це не закодоване припущення про фіксовані числа 0/1.

Невидимість, стінка, відстань, відсутній PlayerObject чи вимкнений сенсор не звільняють слот підключеного клієнта. Disconnect звільняє його слот; інший гравець не переміщується. Нова підключена особа займає вільний слот, залишаючи другого гравця на місці. Понад двох одночасних учасників контракт не представляє: уже призначені слоти не витісняються. Після OnNetworkSpawn/OnNetworkDespawn історія відповідності скидається. При вимкненні компонента без despawn відповідність зберігається до наступного читання й звірки з реєстром.

Слоти визначаються реєстром при читанні. Втрата й повторне використання того самого Client ID між двома читаннями не розрізняється окремим токеном сесії. Повторне використання ID/міграція Host у майбутньому потребуватимуть окремої політики; це не поточний контракт перепідключення між сесіями.

У знімок потрапляє лише результат CopyPlayerPerception.TryObserve: приховані позиції не повертаються. Відсутній/невидимий/від’єднаний гравець дає null. Різниця між цими причинами у числовому векторі навмисно не розкривається. Знімок є копією значень без живих посилань на Transform.

## Порядок 50 ознак

Індекси **0–39** повністю повторюють [draft-1](AI_NPC_DECISION_INPUT_DRAFT.md): live-звук, пам’ять, світло, рівність джерел звуку/світла та чотири known/value-пари контексту.

Індекси **40–44**, гравець A:

- 40 — поточна видимість, 0 або 1;
- 41, 42, 43 — локальні X/Y/Z спостережуваної точки відносно root NPC, поділені на 18 та обмежені до [-1, 1];
- 44 — відстань від root NPC до цієї точки, поділена на 18 та обмежена до [0, 1].

Індекси **45–49** мають ту саму семантику для B. За відсутнього спостереження всі п’ять значень дорівнюють нулю. Відстань у числовому векторі відраховується від root для узгодженості з draft-1; CopyPlayerObservation.Distance є сенсорною відстанню від ока й використовується як перевірені метадані. Координати тіла проходять перевірку скінченності, час — перевірку актуальності. Дубльований Client ID або NetworkObjectId у двох слотах відхиляє весь знімок.

Час, Client ID, NetworkObjectId, список підключених та приховані координати не є числовими входами. Ідентифікатори видимої цілі лишаються метаданими для майбутнього Action Controller. Жодної синтетичної активності гравців не додано.

## Маски семи дій

Індекси дій збережено: Continue 0, InvestigateSound 1, InvestigateLight 2, ObservePlayerA 3, ObservePlayerB 4, AssistMechanism 5, ObstructMechanism 6.

Перші три мають семантику draft-1. ObservePlayerA/B дозволяється лише за поточного видимого спостереження відповідного слоту. Ціль — копія Position та SourceClientId з цього спостереження. Рішення не вибирається C#-кодом. Навігація, повторна перевірка цілі перед виконанням та inference ще не реалізовані цим зрізом.

За рішенням користувача **5 і 6 залишаються закритими** до визначення правил пазла. Читач не використовує стан живлення як дозвіл на допомогу чи перешкоду. Невдалий TryCapture очищає 50 значень і повертає кандидати без дозволених дій, включно з Continue; виклик, який повернув False, не можна подавати моделі.

## Сумісність та навчальна конфігурація

CopyDecisionInput (40) залишається доступним для старих перевірок. Для draft-2 додається CopyDecisionInputV2 до NPC до мережевого спавну; RequireComponent додає потрібні сенсори. Це opt-in: production-сцени й наявну ручну сцену автоматично не змінено. Сенсорний контракт `the-copy.perception/1` теж збережено; новий комбінований знімок має власну назву схеми.

Старий Stage4 ONNX очікує 27 ознак з іншою семантикою. Ані його, ані гіпотетичну 40-вхідну модель не можна використовувати з 50 входами без нового узгодженого Agent/моделі та перевірки inference. Повторне навчання не запускалося, якість політики не виміряна.

[Шаблон PPO](../ai_training/config/the_copy_draft2_ppo.yaml) та [парний контракт](../ai_training/config/the_copy_draft2_contract.json) мають нову назву Behavior `TheCopyDraft2`, 50 входів і дискретну гілку 7. Число входів задається майбутнім Unity Agent/BehaviorParameters, а не YAML. Гіперпараметри скопійовані як початкова чернетка з локального Stage4 seed11; вони не оптимізовані для гри. Шаблон не підтверджений запуском ML-Agents і не має реалізованої reward-функції. Не відновлювати старі Stage4 checkpoints з цією схемою. Пакети, фінальна reward-постановка, навчання й модель потребують наступних задач та погодження там, де це вимагає AGENTS.md.

**Наступна перевірка 2026-11-19:** штатний RunOptions-парсер mlagents 1.1.0 після реєстрації trainer-плагінів прийняв цей YAML. Це перевірка конфігурації без навчального запуску; Agent, reward і Unity-inference ще не перевірені. Фактична ONNX-сигнатура старого Stage4 підтверджена як 27 входів.
